# Authored code statistics — design specification

## Purpose

Add a configurable **Code statistics** block to Expressive Profile. It must
report the programming languages and repositories in which the profile owner
has made commits, not merely the languages present in repositories they own.

The block is generated as the same light/dark SVG assets as the existing
profile cards. It is visible in the editor, included in a downloaded profile
repository, and regenerated by the scheduled GitHub Action.

## Existing system analysis

### Architecture and data flow

The repository has one shared rendering core and two data loaders.

```text
Browser editor                         Installed profile repository
-------------                          ----------------------------
App.tsx                                profile.json
  -> app/data.ts                         -> GitHub Action
  -> Data + Config                       -> action/render.mjs
  -> render/index.ts                     -> src/cli/render.ts source
  -> SVG preview                         -> Data + Config
  -> ZIP                               -> render/index.ts
                                      -> assets/*.svg + README.md
```

`src/render/types.ts` defines the serialisable `Config` and `Data` contracts.
`src/render/index.ts` supplies defaults, creates all SVG assets and builds the
README. `src/render/blocks.ts` contains the individual card renderers.

The editor (`src/app/App.tsx`) owns the configuration and preview state.
`src/app/data.ts` retrieves public GitHub data, builds the ZIP, and embeds the
profile Action workflow. The CLI renderer (`src/cli/render.ts`) is bundled to
`action/render.mjs` by `scripts/renderer.mjs`; the marketplace composite
action (`action.yml`) executes that bundle inside the consumer profile repo.

The site itself is deployed from `main` by `.github/workflows/pages.yml`.
That Pages workflow never handles a visitor token.

### Current statistics semantics

The existing `stats` card shows stars, public repository count, followers,
contribution calendar, and a horizontal language distribution. It calculates
languages from GitHub Linguist byte sizes for owned repositories. In the web
preview this comes from `GET /users/{login}/repos`; in the Action it comes
from GraphQL `Repository.languages`.

This is structurally the wrong source for the requested feature: it measures
the repository contents, not code authored by the person. Adding another
filter to that aggregate would not answer “what languages did I commit in?”.
The new feature therefore has a separate, explicitly named authored-change
pipeline and a separate data model; it does not overload `Data.languages` or
silently alter existing card semantics.

### Existing authentication and privacy

The editor currently works anonymously for public profiles. The separate
device-flow install feature keeps its access token in the browser tab. Its
proxy only forwards device-flow requests. An installed profile may use
`${{ secrets.PROFILE_TOKEN || github.token }}`; the README already documents
that a `PROFILE_TOKEN` gives the Action visibility of private repositories.

The new analysis must preserve these boundaries:

* A pasted PAT is retained only in React memory for the current page session;
  it is never put in `Config`, localStorage, the share URL, ZIP, generated
  README, SVG, console, or an error message.
* The browser calls `api.github.com` directly. GitHub REST API CORS support
  permits this; the project proxy is not extended to relay PATs.
* Long-lived scheduled private analysis is only possible when the user stores
  the PAT themselves as the `PROFILE_TOKEN` Actions secret in their profile
  repository. The generator will show instructions, not attempt to create or
  transmit that secret.

## Scope and non-goals

### Included

* Public-only analysis with no token.
* Expanded analysis of repositories visible to a fine-grained PAT.
* Repositories where at least one qualifying authored commit is found.
* Per-language change volume, per-repository change volume, commit count,
  additions and deletions.
* A Material 3 Expressive SVG card with a donut chart, language legend and a
  compact ranked repository list; light/dark variants and accessible SVG
  title/description.
* Editor controls, English and Russian strings, downloaded configuration,
  scheduled Action support, and a Pages deployment that continues to work.

### Deliberately excluded from the first release

* Persisting or synchronising tokens.
* Claiming to prove that a particular `git push` happened. GitHub repository
  APIs expose commit history, not a personal push audit log. “Repositories I
  pushed to” is defined as repositories containing at least one qualifying
  authored commit reachable from a scanned branch.
* Commit contents, file names, source code, PR data, or contributor rankings
  in any generated output.
* Fork network ancestry analysis and deleted/unreachable branch history.

## User experience

### Entry and token state

The editor adds an **Authored code** section beside the existing Activity
settings. It contains a token field (`type=password`), a clear-token action,
and an analysis action. A compact status chip states one of:

* **Public data** — no token; only public repositories visible to the entered
  login are queried.
* **Private access** — a token was validated; accessible private and
  organisation repositories are included.
* **Needs permission** — the token works but cannot read required repository
  content, with the exact missing permission named.
* **Rate-limited** or **partial** — shows processed/total repositories and a
  safe retry time from GitHub headers.

The field begins empty on each page load. Changing the GitHub login clears the
in-memory token and previous authored analysis, avoiding accidental use of one
account's token for another account.

### Output card

The new optional `authoredStats` block sits after Activity by default. The
card contains:

1. A donut chart for the top five languages, with an “Other” segment when
   needed. Each segment is paired with a text label and percentage; colour is
   never the sole identifier.
2. Three Material-shaped metric tiles: qualifying repositories, qualifying
   commits, and changed lines (`+additions / -deletions`).
3. Up to four ranked repositories showing name, commit count, and changed
   lines. The card title and all labels are customisable/localised.

The card has a no-data state (“No qualifying commits were found”) rather than
an empty or misleading zero chart. It is hidden by default in old saved
profiles until explicitly enabled, preserving existing output.

## Data model

Add a versioned optional model rather than modifying the meaning of existing
fields:

```ts
type AuthoredLanguage = {
  name: string;
  additions: number;
  deletions: number;
  changed: number; // additions + deletions
};

type AuthoredRepository = {
  name: string;
  url: string;
  commits: number;
  additions: number;
  deletions: number;
};

type AuthoredStats = {
  scope: "public" | "authenticated";
  repositoriesScanned: number;
  repositoriesWithCommits: number;
  commits: number;
  additions: number;
  deletions: number;
  languages: AuthoredLanguage[];
  repositories: AuthoredRepository[];
  partial?: { reason: "rate-limit" | "repository-limit"; scanned: number; total: number };
};
```

`Data` gains `authored?: AuthoredStats`. `Config` becomes version 2 and gains
an `authoredStats` presentation section: `enabled`, title and labels,
`chart: "donut" | "legend"`, and `topLanguages`/`topRepositories` limits.
The migration function fills v1 configurations from v2 defaults and leaves the
new block disabled. Its block identifier is added through the existing
`placeNew` mechanism, so profile ordering remains stable.

The renderer consumes only this normalised structure. Fetching, pagination,
authentication, filtering and extension classification live in a new shared
analytics module, so browser and Action cannot drift in their counting rules.

## Analysis algorithm

### Identity and scope

1. Resolve the displayed login. With a PAT, call `GET /user` and require its
   login to match the entered profile login before analysing private data. A
   mismatch is a user-facing error, never a silent cross-account report.
2. Build the author identity set from the viewer login and GitHub commit
   author association. If `user:email` access is available, add the viewer's
   verified e-mail addresses; otherwise e-mail matching is skipped and the UI
   explains that unlinked commits may be absent.
3. List repositories with pagination. Anonymous mode uses public repositories
   owned by the profile login. Authenticated mode lists repositories available
   to the viewer (`owner`, `collaborator`, and organisation-member
   affiliations), including private repositories. Archived repositories are
   included; disabled repositories are recorded as skipped.
4. A repository belongs in the resulting “pushed to” list only after a
   qualifying authored commit has been found. Owning or merely having read
   access to a repository is not enough.

### Commit and file accounting

For each repository, enumerate visible branches, request their commit history,
and de-duplicate commit SHAs across branches. This covers work on feature
branches that is still reachable, rather than only the default branch.

A commit qualifies when either its GitHub `author.login` matches the viewer
login (case-insensitive), or its raw commit-author e-mail matches a verified
viewer e-mail. The committer identity is not treated as authorship. Merge
commits with no changed files contribute neither a language nor changed lines.

For each qualifying SHA, request its commit detail and inspect `files[]`:

* classify a file by exact filename or longest matching extension using a
  pinned, generated mapping from GitHub Linguist metadata;
* include Linguist `programming` and `markup` languages, while excluding
  `data`, `prose` and unknown files from the language denominator;
* exclude binary files and recognised dependency/vendor/generated paths (lock
  files, `node_modules`, common package vendor directories, minified assets);
* add the API-provided `additions` and `deletions` to both the repository and
  the classified language.

The percentage is `language.changed / sum(all recognised language.changed)`.
The denominator includes languages beyond the configured visible top list, so
displayed percentages are never renormalised to an artificial 100%. The UI
provides a plain-language note that it measures changed lines, so refactors
naturally count more than tiny edits. It does not present byte composition as
authorship.

### Pagination, limits, and correctness

All REST list requests follow `Link` pagination. The worker uses bounded
concurrency (four in browser, six in Action), stops before exhausting the
remaining rate-limit budget, and exposes progress after each repository. A
repository or commit detail that returns `403`, `404`, or `409` is skipped and
recorded in the partial-result metadata; it never converts missing access into
zero work.

To keep the first release reliable, default limits are 100 repositories and
5,000 unique commits per run, both configurable only in source for now. The
result declares `partial` if a cap is reached. This is preferable to silently
claiming an incomplete result is “all commits”. Completed browser results are
cached in `localStorage` for seven days under a normalised GitHub login; a new
analysis replaces that value. The cached aggregate may contain private
repository names, so the README tells users how to clear site data. Action
results remain in `.profile/data.json`. Neither cache ever includes a token.

## Token permissions and deployment

The recommended credential is a fine-grained PAT restricted to the intended
repositories with **Metadata: read** and **Contents: read**. Private
organisation repositories may require organisation approval. The UI displays
these requirements before a token is entered and links to GitHub's token page.

GitHub Pages remains a static deployment: `.github/workflows/pages.yml` builds
Vite and deploys `dist`; no secret is added to this repository or its Pages
workflow. GitHub REST supports CORS, so the browser can query GitHub directly.
The installed profile workflow continues to use `PROFILE_TOKEN || github.token`.
With no secret it produces public-only authored metrics. With `PROFILE_TOKEN`,
it can regenerate private-aware metrics on schedule. The generated workflow
must refer to `metawka/expressive-profile@v1` (or another explicitly released
upstream tag), so installed profiles follow the maintained upstream action.

## PAT dialog interaction

The top bar keeps its existing three-part layout: logo, GitHub login and
actions. Authored-code analysis is represented by one compact analytics action
instead of a second input in the bar. Activating it opens the existing Material
dialog surface with a visible PAT label, a private-aware action and a separate
public-only action. The dialog uses the application's existing spring motion,
surface tokens, radii, scrim and reduced-motion behavior. During analysis the
controls are disabled and an `aria-live` progress row reports processed
repositories without resizing the top bar. The PAT remains only in React
memory and is never written to storage or exported files.

## Implementation boundaries

* `src/analytics/` — API client, pagination, identity matching, file
  classification, aggregation. Pure aggregation functions are unit-testable
  without a browser or GitHub token.
* `src/render/types.ts`, `src/render/index.ts`, `src/render/blocks.ts` — data
  contracts, default/migration-safe config, new SVG renderer and README asset.
* `src/app/data.ts`, `src/app/App.tsx`, `src/app/editors.tsx`, `src/app/i18n.ts`
  — token-in-memory UI, progress/error states, preview and controls.
* `src/cli/render.ts` — calls the shared analytics module and persists only
  results to `.profile/data.json`.
* `README.md`, `action.yml`, generated workflow template and test fixtures —
  permission, privacy, secret setup and user documentation.

No code path outside `src/analytics/` may classify files or redefine what an
authored commit is. This prevents a browser preview and Action output from
disagreeing.

## Failure handling

* Invalid, revoked or mismatched PAT: discard it from component state, show a
  non-sensitive error, do not fall back to a false authenticated result.
* Anonymous rate limit: explain the GitHub reset time and retain any previously
  rendered public data as stale, marked data.
* Authenticated rate limit or configured cap: finish the already processed
  aggregate and show it as partial; the SVG includes a “partial data” marker
  when it is exported.
* Empty history, private repositories without token access, or commits with
  only excluded/binary files: show the no-data state.
* One inaccessible repository: continue remaining repositories and name only
  the count of skipped repositories, not private repository names.

## Request efficiency and rate limits

Commit-list requests use GitHub's `author` filter so unrelated history never
reaches the browser. SHA values are deduplicated across branches before commit
details are loaded. A shared request pool processes up to four requests and
three repositories concurrently, with request starts paced below GitHub's
documented secondary REST limit. Response headers are the source of truth for
the current limit, remaining allowance and reset time. The UI reports those
values with repository and commit progress. New work stops with a safety reserve
of 100 authenticated requests (five in the 60-request public window), returning
the aggregate collected so far as partial data.

Preset block lists include `authoredStats`; the full and statistics presets
show it, while presets that intentionally omit it keep it available in the
hidden-block tray instead of dropping it from the profile order.

## Verification plan

1. Unit-test identity matching, SHA de-duplication, Link pagination,
   classification/exclusion and aggregation with fixture API responses.
2. Render fixture `AuthoredStats` into both themes and snapshot the SVG title,
   legend, percentages, no-data and partial states.
3. Run TypeScript checking and `npm run build`; verify the bundle still makes
   `action/render.mjs` before testing the Action.
4. Use a public test account to compare a small repository's known commit
   changes against the output.
5. Run locally with a deliberately restricted token to verify that missing
   access is labelled partial and never leaks the token to a file, archive,
   config, share link, console output or Pages artifact.
6. Push to a test branch and verify the Pages workflow deploys. In a temporary
   profile repository, run the generated workflow both without a secret and
   with a `PROFILE_TOKEN`, then inspect the committed SVG and `.profile/data.json`.

## Acceptance criteria

* A user can generate public authored-code stats without entering a token.
* A matching fine-grained PAT expands the report to accessible private
  repositories without persisting the PAT anywhere.
* The output clearly differentiates public, authenticated and partial scope.
* Language percentages derive from qualifying commit file changes, not
  repository byte sizes.
* Only repositories with qualifying authored commits appear in the ranking.
* The SVG is readable in GitHub light and dark themes and uses Material 3
  Expressive shapes, motion and palette conventions already used by the app.
* Existing v1 profiles continue rendering exactly as before unless the new
  block is enabled.
* The fork's Pages deployment and installed Action work without adding secrets
  to this generator repository.
